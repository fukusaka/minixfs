NAME
     mount_minixfs – mount a MINIX file system image with FUSE

SYNOPSIS
     mount_minixfs [-w [-u always | sync | seconds]] [-M size:heads:side]
                   [FUSE options] image mountpoint

DESCRIPTION
     mount_minixfs mounts the MINIX file system in image on mountpoint through
     FUSE.  It supports V1, V2, V3 and Minix-vmd in either byte order; see
     minixfs(5).

     The mount is read-only unless -w is given, and single-threaded: the
     options -s and -o ro, or -o rw,default_permissions with -w, are always
     given to FUSE.  Inode numbers, modes, link counts, owners, times and
     device numbers are those of the image.  The image may be given as a
     relative path.  Other options, such as -f to stay in the foreground or -o
     allow_other, are passed on to FUSE.

     The options are:

     -w      Mount the file system for writing.  Files, directories, symbolic
             links, hard links, pipes and devices can be made, removed,
             renamed and changed.  The kernel checks permissions against the
             modes and owners in the image.  A new file belongs to the caller,
             but takes the group of its directory where that is set-group-ID,
             as a new directory takes the bit too, or where the inode cannot
             hold the group of the caller, as in V1, whose inodes keep the
             group in a byte.  The mtime and ctime of what changes are set;
             atimes are not.  A file removed while it is open keeps its inode
             and its data, with no name, until it is closed, and then goes.
             Meanwhile libfuse, of Linux and FreeBSD, hides it under a name of
             its own, ‘.fuse_hidden’ and 16 hexadecimal digits: where names
             are of 14 characters, which cannot hold that, the name is kept in
             memory and not in the directory; where they are longer, it is in
             the directory until the file is closed, unless hide=memory is
             given.

             While the file system is mounted, image is locked against other
             programs that write it, such as fsck_minixfs -y, and its clean
             mark is away, as Linux and MINIX 3 take it away; unmounting puts
             it back, unless a change failed in a way that may have left the
             image out of order, such as an error of the device.  A file
             system that is not marked clean, or that has the flex directories
             of Minix-vmd, which this cannot write, is mounted read-only with
             a warning.

     -u always | sync | seconds
             Set when inode and zone bit maps are written:
             sync     At fsync(2) and unmount (the default).
             always   After every change.
             seconds  At fsync and unmount, and on the first change after
                      seconds have elapsed since the last bit map write.
             Data and other metadata are written as they change.  An
             interrupted mount leaves the image unclean; deferred bit maps may
             not match the inodes.  Check and repair it with fsck_minixfs -y.

     -M size:heads:side
             Take an image that holds the file system in the tracks of one
             side of a disk only, as minixfs(1) does.

     -o options
             Besides the options of FUSE, the comma-separated list may hold
             those of mount_minixfs, as mount(8) gives them: rw for -w, ro to
             take that back, update=X for -u X, tracks=X for -M X, and
             hide=memory to keep the names that libfuse hides files removed
             while open under in memory also where names are longer than 14
             characters, or hide=disk, the default, to leave them in the
             directory there.

     The file system is unmounted with ‘fusermount3 -u mountpoint’ on Linux,
     or with umount(8) on the BSDs.

   MINIX 3
     On MINIX 3, mount_minixfs is a service that mount(8) starts, not a
     command.  It is built with ‘make fuse-minix’ and installed as
     /usr/pkg/service/minixfs, and /etc/system.conf is given an entry ‘service
     minixfs’, a copy of that of ntfs-3g.  The image is mounted from a vnd
     device, with the options in -o:

           # vndconfig vnd0 usr.img
           # mount -t minixfs -o rw /dev/vnd0 /mnt
           # umount /mnt
           # vndconfig -u vnd0

     Run by hand, mount_minixfs shows how to mount and exits with 2.  A
     service has no standard error, so its warnings are not seen, and the lock
     is on the vnd device, not on image.

EXIT STATUS
     mount_minixfs exits with 0 when the file system has been unmounted, 1 if
     the image cannot be opened, FUSE fails or the image cannot be written
     back, and 2 for a usage error.

EXAMPLES
     Look at an image:

           $ mount_minixfs usr.img /mnt
           $ ls -l /mnt
           $ fusermount3 -u /mnt

     Copy a tree into an image, with the maps written as they change:

           $ mount_minixfs -w -u always usr.img /mnt
           $ cp -R src /mnt
           $ fusermount3 -u /mnt

BUGS
     On MINIX 3, writing is not reliable, as libpuffs gets the new nodes
     wrong: a symbolic link made through the mount loses its target, a pipe is
     made with no valid type, and a character device is made a block device.

     On NetBSD, a directory made in a set-group-ID directory takes its group
     but not the set-group-ID bit, as librefuse sets the mode that the kernel
     gave once the directory is made.

     On NetBSD 10.0 and later, looking up ‘..’ in a directory right below the
     root fails, and the mount misbehaves from then on, as it does for every
     file system served through librefuse; see docs/netbsd-refuse-dotdot.md in
     the source.

     On NetBSD and MINIX 3, librefuse passes on only the first of the opens of
     a file that overlap, and says a file is closed at the first close.  A
     file removed while open is then kept until the unmount, not until it is
     closed; and a file opened twice, closed once and then removed goes at
     once, so that writing through the other descriptor changes a free inode,
     or a file that took it.

     On FreeBSD, ln(1) through the mount fails with EIO, although the link is
     made: libfuse answers a hard link with a node number of its own for the
     new name, and the fusefs of FreeBSD takes an answer with another node
     number than that of the file for a failure.

     Where the names libfuse hides files under are kept in memory, a file that
     is open and that the user renames to a name of that form is taken for one
     that libfuse hides: the name goes at the unmount, and the file with it
     unless it has another.  A file that is not open is renamed as to any
     other name.

     libfuse gives the link count of a file removed while open one too high
     for a while after its mode, owner or times are changed through it: it
     takes the name it hides the file under off the count it gives for
     fstat(2), but not off the one it gives back for the change, which the
     kernel keeps.
